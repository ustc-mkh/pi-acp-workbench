# Single-host Telegram adapter

The adapter is part of the single production host and shares its format3 SQLite Database with v3 IPC; no legacy session socket or independent Telegram backend exists. The current functional acceptance scope is [workbench-parity-and-simplification-plan.md](workbench-parity-and-simplification-plan.md); evidence and unimplemented workflows are tracked in [feature-parity.md](feature-parity.md) and [workbench-parity-execution.md](workbench-parity-execution.md). Earlier cutover verification is historical, not a declaration of complete parity.

## Configuration

Set `telegram` in the merged configuration. The token is read from the named environment variable and is never stored in JSON:

```json
{
  "bot_token_env": "WORKBENCH_BOT_TOKEN",
  "workspace": "/absolute/allowed/workspace-root",
  "allowed_chat_ids": [-1001234567890],
  "allowed_user_ids": [123456789],
  "inbox_capacity": 128
}
```

- `workspace` must exist. New/attached sessions and operations are restricted to its canonical subtree; symlink escapes are rejected.
- `allowed_chat_ids` must be nonempty. An empty `allowed_user_ids` authorizes all non-bot participants of those chats; use explicit user IDs when that is not intended.
- Bot-origin messages are ignored. Callback identity is never inferred from sender ID or an inline message without an actual chat/topic.
- Default `api_base` is `https://api.telegram.org/`. Plain HTTP is accepted only for an explicitly configured loopback fixture endpoint. Redirects are disabled.
- Bot credentials are removed from ACP child environments, including explicit worker environment overrides using the same variable name. API errors do not retain request URLs or remote descriptions.
- The format3 SQLite storage envelope is not migrated. Use a fresh storage root or export the old root offline and explicitly archive it; no old data or Telegram pending update is implicitly migrated/deleted.

## Commands and interactions

| Input                                          | Behavior                                                                                                                              |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `/new [pi\|codex\|claude] [absolute-path]`     | New session under the allowed root. In forum General, create and bind a new topic; in an existing topic, bind the new session there.  |
| `/open SESSION_ID`, `/attach SESSION_ID`       | Bind an authorized existing session to this topic. Currently one Telegram topic per session.                                          |
| `/sessions`                                    | List sessions under the allowed root.                                                                                                 |
| `/status`                                      | Show session state, settings and **Plan/Todo**. No live Todo notifications.                                                           |
| `/stop`, `/cancel`, `/remove`                  | Cancel the bound turn or remove the bound session.                                                                                    |
| `/model ID`, `/mode ID`                        | Apply a provider-offered setting.                                                                                                     |
| `/answer INTERACTION_ID TEXT_OR_TYPED_JSON`    | Answer a specific interaction without retargeting a newer request.                                                                    |
| `/prompt TEXT`, `//TEXT`                       | Explicit prompt rather than a guessed answer.                                                                                         |
| `/menu [directories\|sessions\|models\|modes]` | Durable inline menu: directory/Harness selection, bounded session/model/mode pages, status/authorization, stop and topic preferences. |
| `/help`, `/start`                              | Text command help.                                                                                                                    |

`/history` exports a recent bounded window; `/history all` starts/resumes chronological export batches (details below). `/sync` exports accessible sessions in bounded pages using the existing topic-effect and history delivery paths; see Sync below. `/notifications [on|off]` controls automatic successful text/image delivery for this topic; `/silent [on|off]` controls Telegram's `disable_notification` flag. Omit the value to query the setting. Only literal `on` and `off` are accepted; there is no non-idempotent toggle.

Ordinary text is classified at admission. With exactly one pending interaction it becomes a validated answer to that interaction; with several it is rejected as ambiguous. A rejected/expired/duplicate answer never becomes a prompt during later execution. Supported permission and single-choice/boolean fields have durable, topic-bound buttons. Multi-field and multi-select answers can use the typed form representation, for example:

```text
/answer INTERACTION_ID {"Form":{"fields":{"name":{"Text":"Ada"},"count":{"Integer":2},"choices":{"Selected":["a","b"]}}}}
```

Only supplied fields supported by the actual definition are accepted. Unknown fields, wrong choices/types, expiry and missing required values are rejected. Decline/cancel buttons are explicit typed responses.

## Interactive menus

`/menu` is a cold projection, not a second command engine. Each button stores an existing typed control and the expected topic binding; acceptance, operation identity, workspace authorization and execution use the same durable inbox path as text commands. Configured harnesses alone appear. Quick New uses the configured authorized workspace; Browse directories selects another existing authorized directory before choosing a Harness. General retains the existing explicit forum-topic creation/uncertain-result rules. There is no Remove button.

- Directory workflow: `/menu` → Browse directories (or `/menu directories`) → directory → Use this directory → configured Harness → New. Pages contain at most 10 visible physical subdirectories, plus next/first/parent navigation; Parent never leaves the canonical authorized root. Hidden/non-UTF-8 directories, symlinks (even internal ones), and regular files are omitted. Enumeration counts all entries toward a 1024-entry cap; overflow produces an explicit omitted/incomplete warning, not a misleading partial directory list. Use the current directory or `/new HARNESS /absolute/path` when listing is unavailable/too large. No directories are created and no file contents are read.
- Directory work runs on a blocking task, with an owned Linux `O_DIRECTORY|O_NOFOLLOW` FD and `/proc/self/fd` enumeration; canonical identity is checked before/after enumeration. FDs are closed per request, never held across user pagination. Name-keyset pages are not a filesystem snapshot: changes before the cursor require First/refresh. The path is reauthorized for navigation, Harness selection, admission and immediately before create/topic effects; a different canonical cwd is not silently substituted. This is not a hostile same-Unix-account sandbox or a network-filesystem latency guarantee.
- Session pages read at most 10 rows using the existing keyset cursor. Unauthorized workspaces are omitted. Sessions bound to another topic are identified in text but have no Open button: one session still has at most one Telegram topic, with no implicit binding transfer. Latest resets the pagination watermark. An individual page can have no openable sessions and still offer Next.
- Model/mode pages expose at most 10 actual **committed provider offerings**. Queries do not start workers, load native sessions or synthesize choices. For a never-run cold session use the menu's Discover provider choices or `/discover`, then reopen Models/Modes. Discovery explicitly starts one provider session, under the existing global worker budget and a ten-second readiness deadline; failure stops/joins that adapter. No business prompt is sent. The ready adapter follows the existing adapter lifecycle. Selecting an offered setting uses the existing configuration operation; this does not add thinking/Fast/arbitrary config options.
- Menu text/choices/expiry are frozen in an immutable reply payload before inbox completion. Delivery retries/restarts reuse that archive and deterministic keys; they do not rebuild a newer menu under an old receipt. Notifications off does not suppress explicit menu replies; silent still applies. The existing topic FIFO/backoff is unchanged.
- Keys expire after 10 minutes, are topic-bound and single-use, and reject after a topic binding change. Current chat/user/workspace authorization is rechecked. Rejection does not consume a different command or reinterpret a button as a prompt. Requests already accepted still retain their original operation semantics.
- Menus allow at most 24 buttons, 64 KiB encoded payload, 12,000 text characters, 64-character labels and 8192-byte commands. At most 3072 Control callback rows coexist within the existing total 4096 callback cap, reserving authorization headroom. Registration reclaims at most 128 expired Control keys at a time, never keys referenced by Pending inbox records; authorization keys are not reclaimed by this online menu path. If full, delivery falls back to command help rather than hiding permission buttons or adding another queue. Offline typed GC remains available.

The complete mobile path has a synthetic binary/Bot contract, including pre-task discovery, queues, authorization, stop/interrupt, restart, history/sync and previews. This is not live phone/provider acceptance; remaining parity differences below still require confirmation.

The pre-release schema now additionally requires `telegram_callbacks.action_kind` and typed `Answer`/`Control` callback bodies. Older experimental roots are rejected, not migrated or reset. Preserve their binary/root together and validate this build with a fresh isolated root.

## Explicit history batches

`/history` and `/history all` reassemble adjacent same-role entries into a provider message only when the provider message identity matches; absent/changed IDs remain separate. The recent window stays bounded to 200 raw committed records, so unusually many Thought/tool records may yield fewer than 20 messages. Thoughts and raw tool text are excluded; tool image captions are not copied as raw tool text.

- Full text is read from immutable content slices (at most 64 KiB at a time) and sent in at most 4000 UTF-16-unit parts; archived bodies are no longer placeholders. Images use the existing checked local archive/multipart path, with no URI/file/remote-fetch fallback. Export text/image parts always set `disable_notification=true`; the small completion/queue summary follows the topic's silent preference. Telegram/client settings still determine visible notifications.
- Request fingerprint checks, cursor advancement, existing outbox intents and the immutable request receipt commit in **one SQLite transaction**. The cursor means durably **planned**, not HTTP-confirmed. Inbox completion and the summary can recover the original receipt after restart without selecting the next batch. The host never prompts/loads a provider or writes a core operation journal for export.
- Stable delivery identities are scoped to `(bot, chat, thread, session, entry)`. Recent/all share dedup; Pending and Acked explicit history entries are not enqueued twice. Recent selects its window before skipping already planned entries, so repeating it does not backfill older entries. Completed automatic Turn pushes now share topic-scoped delivery evidence with explicit history: history skips their Agent entries; automatic rendering skips entries already acknowledged by explicit history. A reserved history entry rechecks automatic evidence again at its FIFO head. Muted/skipped intents and partial/uncertain sends do not count as complete delivery and can still be exported/repeated. Automatic inputs use durable immutable entry references as well: desktop/other-origin input is mirrored, while input originating in this same Telegram topic is acknowledged without echo. Input delivery acknowledgments share history dedup; notifications off may skip automatic input without preventing explicit export.
- Exports use the reserved control class and same-topic mutation FIFO because they advance a cursor/enqueue output; `/status` and other true read queries retain their independent reserve. All sends still use the existing topic FIFO/backoff/eight lanes. There is no second archive, sender or per-part ledger. If every automatic body entry was already exported, one reliable `Turn completed. Output already exported in this topic.` notice remains; dedup does not hide completion. A partial/uncertain send or crash before ack can repeat parts of the current entry; already acknowledged earlier entries are not rerun.
- Accepted export intents retain their original topic, source session label and frozen workspace. They may finish after rebinding or source-session removal; they are not redirected to another topic. Source archives remain readable without a live source snapshot. Scope/chat denial retains explicit exports Pending with InvalidTarget/backoff, rather than ack/discarding their dedup identity; restoring authorization resumes the original intent. Such a deferred head can block later same-topic notices until authorization/target availability is restored. Explicit export cancellation is not implemented.
- `telegram_history_cursors`, `telegram_turn_receipts` and `telegram_history_exports` are required schema tables; `sessions.activity_seq` and `store_meta.activity_seq` provide unique commit-order pagination watermark and are updated atomically with session revisions. `telegram_history_exports` maps every source entry's stable export ID to one grouped-message delivery receipt, so acknowledgment of a reassembled provider message dedups every fragment against later history/automatic output. Older roots missing any current shape fail closed; no migration/reset.

Remaining operational limits: history/sync retain the 200-record per-source scan budget; unknown/partial HTTP sends remain at-least-once and may repeat. Session sync ordering uses a frozen recent-activity watermark; provider-message fragments are reconstructed only when adjacent role/message identity proves they belong together.

## Queues, stopping and previews

The durable inbox is also the input queue, not a second executor. `/prompt TEXT` explicitly queues input while authorization is pending; plain text still answers the pending interaction. Busy topics expose queued update IDs through admission feedback and `/queue`. `/status` and authorization retain reserved lanes. Answer/stop/interrupt can cross waiting prompts, but do not cross intervening configuration/new/history mutations.

`/stop` (`/cancel`) records which earlier pending prompt IDs in the same topic/session are cancelled, then stops the accepted turn using the existing worker fence/join. `/interrupt TEXT` uses the same barrier, stops the old turn and durably accepts replacement input under a separate stable operation ID. Later inputs are not covered by the old barrier. Cancelled inbox rows remain completed with their cancelling update ID. Restart does not replay accepted/unknown provider effects. Only a proven unaccepted Busy receipt can advance to another persisted attempt ID.

Previews are disposable tails: at most eight sessions, 3000 UTF-16 units/session, at most two candidates per scheduler pass, one send/edit per turn every three seconds. They use existing eight sender lanes/topic reservations, after reliable heads, never a per-delta reliable outbox. HTTP has a one-second timeout; failure disables that turn's preview. Lag/restart discards previews. Current authorization, binding, active turn and notifications are checked; previews are always silent. Authorization/errors/final output still use durable delivery and are never replaced by previews.

## Sync

`/sync` in a forum pages through ten accessible session candidates; Next continues the stable list watermark. The first five accessible sessions get up to ten recent eligible entries, older ones up to two (scan cap 200/session). A private-chat sync exports only its bound session and creates no forum topic. Windows are selected before shared dedup, so repeating sync does not backfill older entries.

The frozen plan stores session IDs, cwd, watermark and limits, not bodies. Existing topic bindings are reused; sessions bound to another chat are omitted. Unbound forum sources use a stable per-chat/session topic-effect key: uncertain topic creation needs explicit repair, never a new automatic effect ID. Per-source export receipt/intents are atomic using the existing history/outbox, so interrupted batches recover without rerunning Agents. Explicit sync works with notifications off. A permanently unavailable source/target may stop a page and requires operator attention; no automatic binding transfer is attempted.

## Topic notification preferences

Preferences belong to `(bot, chat, thread)`, including a chat's root topic, not to a session. They may be set before `/new`, survive host restart and session rebinding, and do not change another topic. Only currently authorized chats/users may change or query them. Defaults are notifications **on**, silent **off**. Non-default preferences are capped at 4096 topics per bot; resetting both values to defaults deletes that preference row and frees capacity. No provider is loaded to read or change these settings.

- Notifications off acknowledges/skips optional automatic successful transcript/media intents **when they reach delivery**; it never cancels the Agent, deletes history or rolls back workspace changes. Typed authorization, task errors/control notices, rejection/uncertain-result messages and explicitly requested history/status remain reliable deliveries. Re-enabling does not replay already skipped intents; history remains available explicitly. It is not a time-range filter: an intent not examined until notifications are on again may still send.
- Silent on keeps sending the same messages and media with Telegram `disable_notification=true`, including authorization and explicit command replies. It does not hide content or disable execution. The actual phone's notification behavior still depends on Telegram/client settings.
- Preferences are rechecked between multipart sends. A request already prepared or in flight cannot be recalled; switching notifications off skips later parts at their next preference check. Changing silent affects subsequently prepared requests, not an already-issued request. The preference transaction and remote HTTP acceptance are not an atomic boundary. Partial/uncertain sends remain at-least-once.
- Setting mutations use the reserved control class and preserve same-topic mutation FIFO; read-only setting commands use the query class. The preference and its immutable reply snapshot commit in **one SQLite transaction**. Replaying an admitted old setting/query returns its original reply without overwriting newer preferences. Reply outbox enqueue/inbox completion can then safely finish after restart.
- The existing topic delivery FIFO/backoff is unchanged. A confirmation or explicit query reply can still wait behind a deferred head; preference commands do not bypass retry barriers or create a second sender.

This adds required `telegram_topic_preferences` columns to the current pre-release format-3 schema. Earlier experimental roots without that table/shape are rejected without migration, deletion or reset. Use a new isolated root for validation and preserve the old root/binary as described in the cutover plan.

## Archived image output

Agent image bytes are immutable, independently checksummed payloads; snapshots and public events contain only references. Delivery verifies the expected reference and uploads local bytes with multipart forms: PNG/JPEG via `sendPhoto`, GIF via `sendAnimation`, WebP via `sendDocument`. Filename and MIME derive only from validated archive metadata. Image URIs are never opened/fetched; there is no remote URL or file-id fallback. Decoded input is capped at 4 MiB. Encoding/MIME signature checks are not complete image decoding/sanitization, and local mock acceptance does not prove live Bot media acceptance.

Within a completed turn, archived text/image order is preserved. Text deltas in the same opaque group concatenate; distinct known groups get a paragraph boundary. Standalone image outbox IDs also resolve through the immutable archive. Image uploads share bounded response parsing, redirect refusal and token/description-redacted errors with text requests. A persisted 429 resumes after restart without starting ACP. Partial multi-part success or an uncertain/crash-after-send outcome may duplicate already sent parts on retry: delivery remains **at least once**, not exactly once.

This does not implement incoming photo prompts, tool binary assets or browser media display. The separate trusted local IPC now has an explicit verified `image` archive query; see `docs/workbench-ipc.md`. Bounded parallel cross-topic sending and the durable per-topic retry barrier are described below. Retained archive bytes alone do not grant new topic/workspace authorization. A scoped session delivery can survive external source deletion only while its existing topic binding and current configured workspace authorization remain valid.

## Durability and lifecycle

The finish transaction freezes Agent entry links into immutable `delivery_entries(delivery_id,seq,entry_id)`. TurnStream pages this manifest and slices content, retaining at most one UTF-16-limited text part/image rather than constructing a whole-turn vector. Source deletion/restart does not delete these links. Dispatch reads bindings and heads at one database boundary: target MIN(order_seq), indexed binding resolution, then topic MIN(order_seq). Deferred heads remain barriers; history is not scanned per candidate. Normal offset/pending/admit/complete operations use targeted SQL and never hydrate completed inbox history or a whole TelegramState.

1. Offset, classified inbox command and callback consumption commit in one SQLite transaction.
2. Host commands use the inbox's stable operation ID. Restart replays the original receipt rather than creating another session or running another prompt.
3. `createForumTopic` has its own durable Started/result receipt. An uncertain transport/server outcome is **not retried**: the host cannot know whether Telegram already created the topic. Inspect/reconcile that operation before issuing a new request.
4. Immutable control notices and agent entry/interaction references enter the durable outbox before inbox completion. Retry/429 metadata survives restart and never invokes an agent.
5. Delivery is at least once: a crash after Telegram accepts a message but before durable ack can duplicate that message. Ack tombstones suppress later projection/re-enqueue. Acknowledgement failure never means the intent is discarded.
6. Execution has bounded 8 ordinary / 4 control / 4 query slots. Topic mutations stay FIFO, including pending mutations ahead of later controls. `/status`, `/sessions`, `/help` and rejection notices may read committed state independently of a blocked topic. A busy provider cannot occupy every execution class. Admission/status use bounded queries on the shared database without starting actors; scoped mutations explicitly load their actor.
7. SIGINT/SIGTERM handlers are installed before network startup, and startup/bind failures unwind and join previously started components. Accepted host operations settle; records interrupted at shutdown remain durably classified Pending and recover their original receipts after restart. The host releases storage only after transport and runtime joins. Polling/delivery cancellation interrupts HTTP waits, not admitted inbox/callback/archive/ack file writes. An uncertain send remains Pending and may duplicate on retry, as described above. Normal cancellation waits for flushed ACP cancel/interaction responses before worker stop; unresponsive peers have a bounded forced-stop fallback. Obsolete worker events are fenced.

8. Outbox records now have a durable sequence. A session revision and a Telegram update revision are not comparable. Ack tombstones retain the sequence high-water mark across restart; old storage/body layouts are explicitly rejected without migration. The database storage envelope is format3; use the explicit offline export tool and fresh root rather than expecting earlier layouts to load.
9. The API provides bounded dispatch heads (up to 1024), including records whose retry time has not arrived. A deferred or newly failed head blocks subsequent records resolving to the same topic, including direct command notices behind session images. Other topics can progress past that backoff even after more than 64 queued records. Authorization still precedes rendering. A shared, retained JoinSet owns at most eight delivery jobs, with at most one active job per resolved topic. A slow HTTP request occupies only its lane; other topics can send while capacity remains. Eight occupied lanes apply bounded global backpressure rather than spawning more requests. Binding changes cannot move a scheduled job into another active lane; both old/current active destinations remain reserved until physical completion. Partial multi-part retry remains at least once.
10. Driver drop/abort cancels only its HTTP child token. The shared delivery JoinSet survives and is physically drained by supervision/adapter wait. Polling/execution/delivery sibling handles are also retained outside the supervisor future, so supervisor abort does not abort accepted file transactions. A cancelled cleanup wait can be resumed; the terminal error remains stored until all children/delivery jobs join. A paused-ack regression holds the storage lease through supervisor abort and cancellation of the first wait, then releases it only after ack/join and runtime shutdown. Other tests cover blocked image/other-topic progress, eight/ninth capacity, record-job panic and driver abort. These are local failure regressions, not long soak or a SIGKILL-host guarantee.

11. `DeliveryTarget::Session { session, cwd }` freezes the source workspace with each immutable intent. History validates target scope against its owning session even if the record checksum matches, and rejects workspace changes across revisions. Sender revalidates the frozen cwd against the current configured canonical workspace and resolves the existing authorized topic binding; it does not infer authorization from retained bytes. A missing source snapshot no longer drops an otherwise authorized archived text/image intent. A live snapshot with a different scope is a fatal identity mismatch; denied/unbound destinations do not read/upload image payloads. `/remove` still unbinds the topic; external IPC removal can leave the prior binding for already accepted deliveries. Old target/body layouts are explicitly rejected, not migrated.
12. Cold `inspect` reads return None for missing/deleted sessions; delivery does not turn that absence into `load`, actor creation or a journaled mutation. Regression coverage removes an image-producing source, restarts, sends its original archive bytes to its prior authorized topic and proves no new ACP trace/journal writes. A local actual-binary case combines source deletion, fatal media cancellation, restart and matching-byte delivery with no ACP calls.

## Local verification

```sh
cargo test --manifest-path rust/Cargo.toml -p pi-acp-workbenchd
npm run test:contract:workbench
npm run test:contract:workbench:telegram
```

The last command launches the actual new binary, a local HTTP mock Bot and the independent synthetic ACP peer. Its 27 checks test forum creation, shared IPC events, permission callbacks, wrong-topic/user rejection, persisted text and multipart image 429/restart retry with byte/topic/order verification and no overtaking by later same-topic control notices, bound-topic native resume without an explicit IPC load, child credential isolation, `/status`-only Todo, cross-topic/status progress during a blocked setting, flushed cancellation, other-topic output during a genuinely held image HTTP response, and fatal polling cleanup with both a blocked provider operation and held media HTTP. The cancelled HTTP socket closes and the archived image intent stays Pending; source deletion/restart then verifies frozen scope, original bytes/topic and no ACP rerun. A runtime regression additionally fills all eight ordinary topic lanes, checks query/answer reserves and FIFO, and verifies pending inbox recovery after shutdown. Additional actual-binary checks cover preference persistence across restart without provider activity, muted successful image/text intents with preserved explicit history, and JSON/multipart silent flags without replay on re-enable. SQLite regressions inject reply-insert failure to prove preference/reply rollback, replay old commands after newer settings, enforce topic row capacity and reject incompatible schema without resetting data. Runtime tests cover muted authorization/errors, 429/media restart, multipart preference changes and reserved setting-control progress under eight blocked ordinary lanes. Actual-binary menu checks additionally cover restart-safe configured-harness creation, wrong-topic/user/double-click rejection, real multi-page opening and provider model/mode configuration, and stale controls after rebinding. Runtime/SQL regressions cover cold and stable authorized pages, cross-topic binding protection, workspace revalidation failure without polling failure, frozen/expired menu payloads, callback action mismatch, authorization capacity reserve, Pending-key protection and missing-column root refusal. Directory runtime cases add Unicode/space paths, true page boundaries, hidden/non-UTF-8/file/symlink omission, scan-cap overflow, navigation/rebind rejection, canonical retargeting before create, and restart-safe cold creation. Actual-binary cases repeat directory/Harness selection across restart and refuse an escape without consuming the key or creating a session. History cases additionally use a real binary to stream a complete 600 KiB archived body through 429/restart with notifications off and no ACP, and prove recent/all dedup across restart. Runtime SQL-trigger regressions prove request-receipt rollback, inbox-completion recovery after source removal, full Unicode/image slices, Thought/tool-text omission, scan/cursor capacity limits, missing-schema refusal, and scope-denial retention/restoration. Shared-output checks prove completed automatic text/images are not reexported after restart, and explicit history during a genuinely gated active task suppresses final body/image duplication without suppressing reliable completion. Runtime cases also cover export reservation before automatic ack, fully filtered pages followed by an unseen tail, muted-ack distinction, atomic ack/receipt rollback, destination retention after rebinding and missing-schema refusal. It does not use a real Bot token or establish real-provider compatibility. See `docs/rewrite-verification.md` for remaining acceptance gaps.
